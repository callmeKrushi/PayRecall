PayRecall · How it fits together

Same invoice, same LLM. Memory is the only variable.

PayRecall recommends the next collection action for one overdue B2B invoice. The invoice, the Groq model, and the prompt structure are identical on both runs. The only thing that changes is whether the agent first asks Hindsight what it remembers about this customer, and that is what turns a generic reminder into a specific, cited recommendation.

System architecture

Two execution lanes leave the decision agent. The grey dashed lane never touches memory. The teal lane goes through the Hindsight bank first. Both lanes end in the same shared LLM.

Request flow, step by step

  1. The collector selects a customer and one of their overdue invoices in the Streamlit UI.
  2. The application identifies the customer record and invoice from data/customers.json and validates that they belong together.
  3. The decision agent selects the execution path from the memory toggle. Both paths receive the same invoice summary and the same basic profile.
  4. On the memory-enabled path only, the agent retrieves customer context from Hindsight: recalled memories with strict customer tags, the customer playbook mental model, and a reflect assessment. Each recalled memory is given a short reference id.
  5. The Groq LLM produces one structured recommendation: channel, recipient, tone, approach, timing, rationale, confidence, and the evidence ids it relied on. The UI renders it and, on the memory path, lists the cited memories.
Memory off

Direct execution, no customer memory

The agent builds the prompt from the invoice and a profile limited to active contacts, terms, and industry. It does not read from or write to Hindsight, and confidence is capped at 0.4 because there is no evidence.

Memory on

Retrieve context, then generate

The agent adds recalled memories, the playbook, and the reflect assessment to the same prompt structure, asks the LLM to cite the evidence ids it used, and maps those ids back to the memories shown in the UI.

Learning loop

A logged outcome becomes new memory, and the same invoice is planned again so the change is visible.

Memory concepts

What each Hindsight capability contributes, and how PayRecall calls it.

Retain / Retain Batch

Narrative interaction notes go in as plain text and Hindsight extracts the facts. Historical records are seeded in batches; live outcomes are retained one document at a time.

retain_batch for the 35 seeded records with fixed document ids, so a second seeding sends nothing · retain with update_mode="replace" for live outcomes · tags: customer, invoice, channel, actor, outcome

Recall

Returns the memories relevant to a query, restricted to one customer. Untagged memories and other customers are excluded, which is what keeps histories isolated.

recall(tags=["customer:<id>"], tags_match="all_strict") · observations ranked first, then raw facts · capped at 15 memories in the prompt

Observations

Consolidated beliefs that Hindsight derives from many facts, such as "emails to the shared inbox are ignored" or "a firm notice caused a dispute". They update automatically after each retain.

observations mission asks for per-customer channel, contact, tone, and timing patterns, keeps contradictions, prefers recent evidence · observation layer rebuilt once under that mission

Mental Model

The customer playbook. Hindsight writes it from a source query over the customer's memories and refreshes it after consolidation and after each logged outcome. It is shown verbatim in the UI.

create_mental_model(id="playbook-<customer>", tags=["customer:<id>"], trigger={"refresh_after_consolidation": true}) · the model's tags are its reflect scope

Reflect

An evidence-based assessment produced by Hindsight over the same customer scope. It is fed to the LLM alongside the raw memories, and its source facts are merged into the evidence list.

reflect(tags=["customer:<id>"], tags_match="all_strict", include_facts=True) · retried once on a server-side failure

Bank Configuration

Missions steer what Hindsight extracts and how it reasons; disposition keeps reflect factual and cautious about inventing preferences.

update_bank_config: observations_mission, reflect_mission, disposition_skepticism 4, disposition_literalism 4, disposition_empathy 3

Implementation notes

  • All customers, contacts, invoices, and interactions are fictional. The dataset exists for demonstration only.
  • The action step is a mock. No email, WhatsApp, telephony, or ERP integration exists; outcomes are typed into the UI.
  • Hindsight directives were planned but not implemented. Only the demo customer has a generated playbook unless others are created.
  • Requires Hindsight Cloud and a Groq API key. LLM output varies between runs; JSON mode falls back to plain-text parsing when the provider rejects it.
  • Single user, single bank, no authentication.
